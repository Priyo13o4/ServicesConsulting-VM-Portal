# Codebase Structure & File Placement Guide

This guide is the authoritative reference for developers on where each **type of file** lives, what responsibility it has, and where to place new code.

---

## 1. High-Level Architecture: Frontend & Backend Split

The repository enforces a strict boundary between the **Frontend (UI & routing)** and the **Backend (domain services & queries)** so teams can develop simultaneously without merge collisions:

```
src/
├── app/                  ← FRONTEND: Next.js pages, layouts, and route handlers (THIN)
├── modules/<feature>/    ← BACKEND + UI: Domain services, queries, actions, and feature components
├── db/                   ← DATABASE: Drizzle tables, migrations, and query helpers
├── lib/                  ← SHARED: Cross-cutting utilities (router, security, cache, crypto)
└── components/ui/        ← DESIGN SYSTEM: Reusable UI widgets (shadcn/ui, buttons, tables)
```

---

## 2. File Types & Placement Rules

### 🌐 Frontend Layer — `src/app/`
**Rule:** Pages must stay completely thin. No business logic, no direct SQL/DB calls, no secrets.

| File Type | Path Pattern | Responsibility |
|---|---|---|
| **Page** | `src/app/**/page.tsx` | Next.js Server Component. Fetches data via `queries.ts` and renders feature components. |
| **Layout** | `src/app/**/layout.tsx` | Visual framing, header, navigation, and sidebar wrappers. |
| **Route Handler** | `src/app/api/**/route.ts` | Non-action HTTP endpoints (health checks, webhooks, CSV downloads). |
| **Global Styles** | `src/app/globals.css` | Tailwind 4 theme definitions and base styles. |
| **Root Proxy/Middleware** | `src/proxy.ts` / `src/middleware.ts` | Optimistic redirects for unauthenticated users. |

---

### ⚙️ Domain Modules — `src/modules/<feature>/`
Each business domain (`auth`, `users`, `requests`, `approvals`, `vms`, `tickets`, `workflow`, `queue`, `settings`) lives in its own folder.

| File Type | File Name | What goes here |
|---|---|---|
| **Validation Schema** | `schema.ts` | Zod schemas shared between frontend form validation and backend server action parsing. |
| **Business Service** | `service.ts` | Pure TypeScript business logic. Takes `db` + input, returns `Result<T>`. Never imports Next.js. |
| **Queries** | `queries.ts` | Read-only database access functions, always scoped to caller's role and user ID. |
| **Server Actions** | `actions.ts` | `"use server"` mutations: calls `requireUser()` → parses Zod schema → calls `service.ts` → calls `revalidateEntity()`. |
| **Feature Components** | `components/*.tsx` | React components specific to this feature (e.g. `RequestForm.tsx`, `ApprovalDecisionModal.tsx`). |
| **Client UI Store** | `store.ts` + `store-provider.tsx` | Zustand client store factory (only when multiple components share client-only UI state). Never holds server data. |
| **Unit Tests** | `<feature>.test.ts` | Vitest tests for the feature's business logic and validation rules. |

---

### 🗄️ Database Layer — `src/db/`

| File Type | Path Pattern | Responsibility |
|---|---|---|
| **Table Schemas** | `src/db/schema/*.ts` | Drizzle ORM table definitions (`casing: "snake_case"`, camelCase TS keys). |
| **Database Client** | `src/db/client.ts` | Singleton connection via `postgres.js` with `prepare: false` for PgBouncer transaction mode. |
| **DB Helpers** | `src/db/helpers.ts` | Pagination (`buildPagination`), query metadata, and transaction helpers. |
| **Migrations** | `src/db/migrations/*.sql` | Generated by `npm run db:generate`. **Never edit manually.** |

## 3. Quick Lookup: "Where Does My Code Go?"

| What are you adding? | Where does it go? |
|---|---|
| A new database table or column | `src/db/schema/<entity>.ts` |
| A database query to read data for a screen | `src/modules/<feature>/queries.ts` |
| Business rules, validation logic, or state transitions | `src/modules/<feature>/service.ts` |
| Form fields and validation rules | `src/modules/<feature>/schema.ts` |
| A button action or form submission | `src/modules/<feature>/actions.ts` |
| A full page URL (e.g. `/my-page`) | `src/app/(portal)/my-page/page.tsx` |
| A reusable button, modal, or input component | `src/components/ui/` |
| A feature-specific table or form component | `src/modules/<feature>/components/` |
| A new route path constant | `src/lib/router.ts` |
| Unit tests for business logic | `src/modules/<feature>/<feature>.test.ts` |

## 4. Development Workflow: Adding a New Feature

When building a new capability (e.g. creating a ticket or submitting a request):

1. **Schema (`src/modules/<feature>/schema.ts`)**: Define the Zod schema for the input.
2. **Service (`src/modules/<feature>/service.ts`)**: Write the business logic function returning `Result<T>`.
3. **Tests (`src/modules/<feature>/<feature>.test.ts`)**: Write failing unit tests first, then make them pass.
4. **Action (`src/modules/<feature>/actions.ts`)**: Wrap the service with `requireUser()`, schema parsing, and `revalidateEntity()`.
5. **Component (`src/modules/<feature>/components/`)**: Build the UI form or table using the shared Zod schema.
6. **Page (`src/app/(portal)/.../page.tsx`)**: Import queries for initial data and mount the component.
